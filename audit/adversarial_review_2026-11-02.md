# Forever Trade — адверсариальное ревью

Дата: 2026-11-02

What this repo does: Forever Trade читает цены из `Auctionator.lua`, сохраняет историю в SQLite, рассчитывает торговые сигналы и генерирует локальный HTML-портал с AI-рекомендациями. Ревью исходит из модели: один локальный пользователь, игровой клиент перезаписывает Lua, обычно работает один watcher, но случайный второй процесс возможен.

Проведено пять агентных проходов, включая финальное независимое опровержение выводов. **Все 160 тестов прошли**, ручной сценарий `Lua → SQLite → portal.html` тоже прошёл. Это не отменяет дефекты ниже: опасные ветки тестами не проверяются.

В рабочей базе: 136 снимков, нулевых и будущих цен нет. Последнему снимку на момент проверки около **45 часов** — при стандартном TTL 48 часов без нового сканирования сигналы скоро исчезнут.

## Must fix

### 1. Waylaid показывает прибыль там, где реальный убыток

**Расположение:** `src/analytics.py:521`

- **Что это:** Стоимость сырья для сдачи ящика NPC должна полностью рассчитываться по цене аукциона.
- **Проблема:** Код заменяет её на `min(AH, vendor_buy)`. Воспроизведение: AH=`100`, NPC=`10`, 20 предметов, награда=`1000` — портал считает `+800`, хотя реальная прибыль `1000−20×100=−1000`.
- **Исправление:** Для raw turn-in требовать `p_out > 0` и использовать только `target_count × p_out`. Добавить этот числовой регрессионный тест.
- **Если пропустить:** Пользователь получает прямой сигнал к убыточной покупке.

### 2. «Строгий белый список» вендорных реагентов фактически не работает

**Расположение:** `src/analytics.py:376`

- **Что это:** Цену NPC разрешено подставлять только для проверенных реагентов из `VENDOR_REAGENTS_WHITELIST`.
- **Проблема:** Достаточно иметь `vendor_buy_price > 0` или категорию `vendor`/`vendor_reagent`. Для Raw Sunscale Salmon крафт показывает `+3957,5` вместо `−42,5` при закупке по AH.
- **Исправление:** Разрешать NPC-цену только по ID из белого списка; остальные реагенты считать по AH. Проверить несколько не входящих в список ID.
- **Если пропустить:** Дикие ресурсы и предметы с ограниченной продажей у NPC порождают ложную маржу.

### 3. Нулевая цена превращается в торговый сигнал

**Расположение:** `src/analytics.py:207`, `src/analytics.py:714`

- **Что это:** Вендорный арбитраж и Z-score используют сохранённые цены без повторной проверки на положительное значение.
- **Проблема:** Воспроизведены `VENDOR_SHUFFLE` с покупкой за `0` и прибылью `200`, а также `STRONG_BUY` с нулевой текущей ценой и расчётной прибылью `64,17`.
- **Исправление:** Отбрасывать `price <= 0` до выборки последнего лота и до формирования статистического окна. Добавить тесты на ноль в текущем и историческом снимках.
- **Если пропустить:** Повреждённые данные выглядят как гарантированная прибыль.

### 4. Незавершённая запись Lua импортирует старую резервную копию

**Расположение:** `src/etl.py:636`, `src/etl.py:680`

- **Что это:** Watcher должен ждать стабильного размера и закрывающей `}` перед парсингом.
- **Проблема:** После всех попыток `_wait_for_file_ready()` всё равно возвращает `True`. Воспроизведено: после цены `200` незавершённый primary и свежий `.bak` со `100` добавляют старую цену как новую.
- **Исправление:** Возвращать `False` и прерывать ETL, если файл не стал завершённым. Не принимать резервную генерацию старше последней импортированной.
- **Если пропустить:** Портал перестраивается по смешанным поколениям данных и показывает несуществующие сделки.

### 5. Автоопределение реалма навсегда переключает watcher на чужой реалм

**Расположение:** `src/etl.py:330`, `src/etl.py:704`, `run_watcher.py:167`

- **Что это:** При отсутствии настроенного реалма ETL выбирает словарь с наибольшим числом предметов.
- **Проблема:** После Horde-only файла handler записывает `self.realm="Horde"`. Следующий файл с Alliance и Horde снова импортирует Horde, а аналитика продолжает запрашивать исходный Alliance.
- **Исправление:** Не изменять настроенный реалм watcher. Если автовыбор нужен, выполнять его один раз при старте и передавать выбранный реалм во все вызовы.
- **Если пропустить:** База наполняется чужими ценами, а портал пользователя остаётся пустым или устаревшим.

### 6. При `realm=None` смешиваются цены разных реалмов

**Расположение:** `src/analytics.py:271`, `src/analytics.py:502`

- **Что это:** `latest_prices` индексируется только по `item_id`, хотя запрос возвращает строки нескольких реалмов.
- **Проблема:** Воспроизведено: продукт Everlook за `200` соединяется с реагентом Warsong за `10` вместо Everlook за `190`; отображается `+165` вместо реальных `−15`.
- **Исправление:** Либо обязательно требовать реалм, либо вести расчёт отдельно по ключу `(item_id, realm)` и сохранять реалм в результате.
- **Если пропустить:** Прямые вызовы аналитики без реалма создают несуществующий арбитраж.

### 7. Историческая цена выбирается по порядку записей, а не по времени

**Расположение:** `src/etl.py:449`

- **Что это:** При отсутствии текущих полей `m`/`mr` ETL использует исторические таблицы `h`/`l`.
- **Проблема:** Для `{1700000000:780, 1700003600:900}` сохраняется первое значение `780`, хотя последнее — `900`.
- **Исправление:** Выбирать значение с максимальным числовым timestamp; повреждённые ключи пропускать. Добавить тест с обратным порядком записей.
- **Если пропустить:** Вся последующая аналитика опирается на произвольную историческую цену.

### 8. AI выбрасывает уже рассчитанные сигналы watcher’а

**Расположение:** `src/ai_advisor.py:137`, `run_watcher.py:177`

- **Что это:** Watcher передаёт в `build_compact_context()` списки арбитража, крафта и аномалий с учётом TTL и перков.
- **Проблема:** Параметры попадают в неиспользуемый `**kwargs`; функция повторно читает БД с настройками по умолчанию. Переданный вендорный сигнал в воспроизведении исчез полностью.
- **Исправление:** Использовать переданные списки; при их отсутствии явно пробрасывать TTL и перки в аналитические запросы.
- **Если пропустить:** AI советует по другому набору данных, чем таблицы портала.

### 9. API-ключ передаётся на другой хост после HTTP-перенаправления

**Расположение:** `src/ai_advisor.py:337`

- **Что это:** Ключ Gemini добавляется в заголовок `x-goog-api-key`, после чего используется стандартный redirect-handler `urllib`.
- **Проблема:** Локальный тест с двумя серверами подтвердил: после `302` второй origin получил `x-goog-api-key: secret-marker`.
- **Исправление:** Запретить redirects для этого запроса либо разрешать только same-origin HTTPS и удалять заголовок при смене origin. Добавить двухсерверный тест.
- **Если пропустить:** Перенаправление или небезопасно настроенный endpoint могут раскрыть ключ.

### 10. Обычный тест перезаписывает рабочий каталог предметов

**Расположение:** `tests/test_database.py:959`

- **Что это:** Тест открывает `data/items_forever.json` на запись и подменяет его одним тестовым предметом.
- **Проблема:** Если файл существовал, `finally` его не восстанавливает и даже не удаляет. При обычном запуске pytest исходный каталог остаётся потерянным.
- **Исправление:** Использовать `tmp_path` или переданный путь каталога; тесты не должны открывать рабочие данные на запись.
- **Если пропустить:** Следующий запуск приложения получит каталог из одного фиктивного предмета. В этом аудите файл защищён копией; SHA-256 до и после совпал.

### 11. Рецепты с выходом больше одного предмета считаются неверно

**Расположение:** `src/analytics.py:411`, `src/analytics.py:423`

- **Что это:** Выручка умножается на `expected_yield`, но стоимость упаковки и депозит продолжают предполагать один результат крафта.
- **Проблема:** При yield=`2`, цене=`100`, сырье=`50`, депозите=`100` код показывает `+40`; продажа двух единиц с двумя депозитами даёт `−60`. Для Waylaid десять предметов при yield=2 требуют пять крафтов, а не десять.
- **Исправление:** Делить `pack_craft_cost` на ожидаемый выход и применять согласованную модель депозита на единицу/лот. Добавить числовые тесты yield=2 и Master Chef.
- **Если пропустить:** Прибыль многовыходных рецептов искажается в обе стороны.

### 12. Карточка «Топ Снайп» завышает прибыль на депозит

**Расположение:** `src/dashboard.py:637`

- **Что это:** Аналитика уже рассчитала `expected_net_profit` с комиссией и депозитом, но карточка пересчитывает прибыль самостоятельно.
- **Проблема:** При средней=`91,67`, текущей=`50`, депозите=`15` карточка показывает около `+37` вместо `+22,08`.
- **Исправление:** Использовать `expected_net_profit` для сортировки и отображения. Проверить равенство карточки и аналитики.
- **Если пропустить:** Пользователь видит большую прибыль, чем та, которая прошла проверку безубыточности.

### 13. Вкладка Strong Buy показывает сигналы STRONG_SELL

**Расположение:** `src/dashboard.py:611`, `src/dashboard.py:805`, `src/dashboard.py:1543`

- **Что это:** Счётчик вкладки строится по `strong_buys`, а тело таблицы — по всем `anomalies`.
- **Проблема:** Воспроизведён случай: счётчик равен `0`, но внутри активной вкладки Strong Buy находится строка «Sell only».
- **Исправление:** Передать в эту таблицу `strong_buys`; либо переименовать вкладку и счётчик во «Все аномалии».
- **Если пропустить:** Подпись интерфейса противоречит рекомендуемому действию.

### 14. Shopping List повторно рассчитывает Z-score по старой истории

**Расположение:** `src/dashboard.py:394`, `src/dashboard.py:1929`

- **Что это:** Экспорт использует клиентский `ITEM_STORE.z_score`, рассчитанный по всем снимкам без TTL, лимита окна и проверки прибыли.
- **Проблема:** Предмет, исключённый серверной аналитикой из-за TTL, всё равно удовлетворяет условию экспорта `z_score <= -1.8`.
- **Исправление:** Передавать в JavaScript явные ID текущих STRONG_BUY и выгодных лотов, предусмотренных спецификацией; не повторять аналитику в браузере.
- **Если пропустить:** В список закупок попадают предметы, которые текущая модель не признала покупкой.

### 15. Вкладка Waylaid смешивает две разные экономические модели

**Расположение:** `src/dashboard.py:654`, `src/dashboard.py:737`

- **Что это:** Raw-строки показывают стоимость комплекта и награду NPC, а crafted-строки — прибыль одного крафта на AH.
- **Проблема:** В проверенном fixture crafted-строка показывает прибыль `535`, хотя прибыль сдачи соответствующего ящика — `7000`; сырьевые строки используют другой смысл тех же колонок.
- **Исправление:** Для ящиков выводить `pack_cost`/`pack_craft_cost`, `reward_copper` и turn-in profit; обычный крафт оставить в отдельной вкладке.
- **Если пропустить:** Сравнение и ранжирование ящиков бессмысленны.

## Should fix

### 16. Задокументированный разовый запуск не существует

**Расположение:** `run_watcher.py:141`

- **Что это:** Основная инструкция предлагает `python run_watcher.py --run-once --realm "Everlook"`.
- **Проблема:** Реальный запуск завершился `argparse: unrecognized arguments: --run-once`, код выхода `2`.
- **Исправление:** Реализовать ранний выход после ETL и генерации портала; добавить CLI-тест через subprocess.
- **Если пропустить:** Основной безопасный сценарий запуска из документации не работает.

### 17. Большой Lua integer обрывает импорт с необработанным `OverflowError`

**Расположение:** `src/etl.py:413`, `src/etl.py:530`

- **Что это:** ID и цены проверяются на положительность, но не на верхнюю границу SQLite INTEGER.
- **Проблема:** ID `9223372036854775808` воспроизводит `OverflowError: Python int too large to convert to SQLite INTEGER`; обработчики ловят только `sqlite3.Error`.
- **Исправление:** Ограничивать ID и цены допустимыми диапазонами до SQL и перехватывать ошибки преобразования на границе записи.
- **Если пропустить:** Один повреждённый или вредоносный лот останавливает стартовый импорт и последующие обновления.

### 18. Дедупликация не атомарна между двумя watcher-процессами

**Расположение:** `src/etl.py:370`, `src/etl.py:494`, `src/etl.py:567`

- **Что это:** Метаданные и последние цены читаются до транзакции записи.
- **Проблема:** Два процесса могут одновременно прочитать одинаковое состояние, оба пройти проверки и вставить одинаковые снимки; WAL лишь сериализует записи, но не отменяет устаревшее чтение.
- **Исправление:** Начинать `BEGIN IMMEDIATE` до чтения metadata/latest и держать транзакцию до обновления metadata. Добавить тест с двумя соединениями.
- **Если пропустить:** Дубли искажают окна Z-score и вызывают повторные перестроения портала.

### 19. Ошибка загрузки overrides навсегда блокирует повторную попытку

**Расположение:** `src/analytics.py:38`, `src/analytics.py:80`

- **Что это:** `_OVERRIDES_MTIME` обновляется до чтения JSON и коммита, исключения проглатываются, функция возвращает `True`.
- **Проблема:** После повреждённого обновления исправленный файл с тем же mtime уже не загружается; в БД остаются старые награды и прибыль.
- **Исправление:** Обновлять mtime только после успешного коммита, при ошибке возвращать `False`. Добавить тест «ошибка → исправление с тем же mtime».
- **Если пропустить:** Портал продолжает торговые рекомендации по старым правилам сервера.

### 20. Autopilot может завершить одноимённый процесс другого проекта

**Расположение:** `.autopilot/ap.py:515`, `.autopilot/ap.py:567`

- **Что это:** Признаком «нашего» процесса служит просто наличие `serve_permanent.py` в командной строке.
- **Проблема:** `python /other/project/serve_permanent.py` также попадает под `kill_orphans()` и получает сигнал завершения.
- **Исправление:** Сравнивать нормализованный абсолютный путь скрипта и PID из собственного PID-файла. Добавить тест на чужой каталог.
- **Если пропустить:** Обычная очистка autopilot может прервать unrelated работу пользователя.

## Итог

Ещё 11 менее приоритетных случаев и замечаний по устойчивости не развёрнуты из-за лимита отчёта. Код не изменялся; временные fixtures и базы удалены.

**Verdict:** Сначала исправить 1–5 и 10: они напрямую создают убыточные сигналы, импортируют неправильные данные или уничтожают каталог; зелёные 160 тестов сейчас не являются доказательством корректности торговли.

**Not checked:** Внешние WoW/Forever ID, награды и доступность товаров у NPC не сверялись с авторитетным игровым источником; живые Gemini/Wowhead не вызывались; поведение проверено на локальных fixtures, а не на реальном игровом клиенте. Кросс-модельная проверка через внешний CLI не запускалась.
