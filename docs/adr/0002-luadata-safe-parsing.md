# 0002. Безопасный синтаксический анализ Auctionator SavedVariables через luadata с отказоустойчивым .bak fallback

## Контекст
Аддон `Auctionator` для World of Warcraft сериализует свою базу цен `AUCTIONATOR_PRICE_DATABASE` в файл `WTF/Account/<ACCOUNT>/SavedVariables/Auctionator.lua`. Запись на диск выполняется игровым клиентом при смене персонажа, выходе из игры или при ручном вызове консольной команды `/reload`.

Специфика источника данных создает ряд технических рисков:
1. Файл содержит специфический синтаксис таблиц языка Lua (включая квадратные скобки строковых ключей `["Linen Cloth"]`, суточные срезы `H5812`/`L5812`, комментарии `--`).
2. При аварийном закрытии клиента WoW или внезапной перезагрузке системы файл `.lua` может оказаться записан не полностью, иметь усеченный конец или содержать синтаксический мусор.
3. Обработка недоверенного текста из внешнего файла потенциально уязвима для атак на выполнение произвольного кода, если используются небезопасные механизмы динамической интерпретации.

## Решение
Реализован специализированный модуль синтаксического анализа на базе библиотеки `luadata` с каскадной отказоустойчивостью:
1. **Безопасная десериализация без `eval()`:**
   Использование чистого парсера `luadata`, строящего абстрактное синтаксическое дерево литералов таблиц Lua без выполнения кода в среде Python.
2. **Алгоритм извлечения таблицы по балансу скобок (`_extract_lua_table`):**
   При наличии в файле сторонних переменных или служебного заголовка парсер точно локализует границы блока `AUCTIONATOR_PRICE_DATABASE = { ... }` с учетом экранирования строк и блочных/строчных комментариев Lua (`--[[ ... ]]` и `--`).
3. **Многоуровневый каскад парсинга:**
   - Попытка прямого чтения через `luadata.read(file_path)`;
   - При сбое — изолированное извлечение таблицы и вызов `luadata.unserialize(extracted)`;
   - При сбое — попытка десериализации всего содержимого через `luadata.unserialize(content)`.
4. **Отказоустойчивый fallback на `.bak` файл:**
   При любой ошибке парсинга основного файла (`Auctionator.lua`) система автоматически переключается на чтение резервных копий `Auctionator.lua.bak` / `Auctionator.bak`, генерируемых клиентом WoW. Ошибка логируется с уровнем `WARNING`, а успешная загрузка копии фиксируется в `watcher.log`.
5. **Нормализация идентификаторов (`normalize_item_id`):**
   Извлечение чистого целочисленного `item_id` из сложных строковых сигнатур вида `"2589:0:0:0:0"`, исключая оверхед строкового сравнения в SQL.

## Почему (что рассмотрели и отвергли)
- **Использование `eval()` или Python `exec()` через текстовую замену синтаксиса:**
  Категорически отвергнуто. Представляет критическую уязвимость удаленного выполнения кода (RCE).
- **Парсинг регулярными выражениями (Regex):**
  Отвергнут. Регулярные выражения принципиально не способны надежно разбирать произвольно вложенные рекурсивные структуры данных таблиц Lua, легко ломаются на строковых ключах со спецсимволами и имеют катастрофический backtracking на больших файлах баз цен (размером в десятки мегабайт).
- **Встраивание полноценного рантайма Lua (Lupa / LuaJIT):**
  Отвергнуто в соответствии с принципом Ponytail. Требует компиляции нативных бинарных библиотек C под целевую ОС (Windows), усложняет установку зависимостей через `pip` и несет избыточный оверхед по памяти.
- **Отказ от механизма `.bak` fallback:**
  Отвергнут, так как первый же аварийный сбой игрового клиента приводил бы к остановке фонового процесса ETL и потере рыночной аналитики.

## Последствия
- **Положительные:**
  - Полная безопасность исполнения: парсер не выполняет внешний код.
  - Высокая надежность: битый файл `.lua` не останавливает работу сервиса — данные прозрачно извлекаются из `.bak`.
  - Корректная обработка всех форматов ключей и вложенных структур данных `Auctionator`.
- **Отрицательные:**
  - Десериализация очень больших баз цен в памяти Python может занимать до 200–400 мс на замер (компенсировано 10-минутным окном дедупликации, отсекающим избыточные повторные парсинги).
