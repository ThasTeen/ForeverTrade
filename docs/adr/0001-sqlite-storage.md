# 0001. Выбор встроенной SQLite 3 с индексами временных рядов вместо внешних СУБД

## Контекст
Аналитическому агенту `Forever Trade` требуется хранить и непрерывно обрабатывать рыночные данные сервера World of Warcraft: Forever:
- статический каталог базовых предметов Classic Era 1.15 (`data/items_era_1_15.json`);
- слой оверрайдов и модификаторов Forever (`forever_overrides.json`, контейнеры снабжения Waylaid Crates, биваки);
- граф ремесленных рецептов и реагентов для 5 ключевых профессий;
- непрерывный поток срезов цен аукциона (`price_snapshots`), поступающий из аддона `Auctionator.lua`.

Агент работает локально на пользовательской рабочей станции совместно с запущенным клиентом игры. Требуется локальное, надёжное и транзакционное хранилище, обеспечивающее высокую скорость аналитических агрегаций (оконные функции, поиск последних срезов цен, расчет Z-score) без накладных расходов на администрирование внешних инфраструктурных сервисов.

## Решение
Выбрана встроенная бессерверная СУБД SQLite 3 (файл `market.db`) со следующими архитектурными параметрами:
1. **Режим журналирования WAL (Write-Ahead Logging)** и включение поддержки внешних ключей:
   ```sql
   PRAGMA foreign_keys = ON;
   PRAGMA journal_mode = WAL;
   ```
   Это обеспечивает параллельные неблокирующие чтения во время пакетной вставки новых снимков цен.
2. **Схема с составными B-tree индексами** под паттерны доступа временных рядов:
   - `idx_snapshots_item_time` на `price_snapshots(item_id, timestamp)` — для мгновенного извлечения последних цен и расчета скользящего окна Z-score;
   - `idx_snapshots_realm_time` на `price_snapshots(realm, timestamp)` — для изоляции снимков по игровым мирам и фракциям.
3. **Механизм ротации и скользящего окна хранения данных:**
   Функция `prune_snapshots(conn, max_days=30)` удаляет записи старше 30 дней, предотвращая деградацию индексов и неограниченный рост размера файла БД на диске.
4. **Пакетная вставка (Batch Ingestion):**
   Использование метода `executemany` внутри единой транзакции при разборе снимка аукциона, что обеспечивает запись тысяч лотов за доли секунды.

## Почему (что рассмотрели и отвергли)
- **Внешние реляционные СУБД (PostgreSQL / MySQL):**
  Отвергнуты в соответствии с принципом Ponytail и нулевых внешних зависимостей. Требуют установки отдельного сервера, настройки пользователей, паролей, сетевых портов и фонового демона. Это создает барьер для запуска конечным пользователем и потребляет ценную оперативную память, необходимую игровому клиенту.
- **Хранение в плоских файлах (JSON / CSV / Parquet):**
  Отвергнуто из-за отсутствия транзакционных гарантий (ACID), риска повреждения файлов при аварийном завершении работы системы или одновременном доступе, а также неприемлемо высокой алгоритмической сложности: поиск последнего среза цен по предмету в JSON требует полного сканирования файла ($O(N)$ вместо $O(\log N)$ в B-tree индексе SQLite).
- **Специализированные TSDB (TimescaleDB, InfluxDB):**
  Отвергнуты как крайняя степень оверинжиниринга для локального десктопного инструмента одного игрока.

## Последствия
- **Положительные:**
  - Полная автономность: база содержится в единственном файле `market.db`, переносимом между каталогами.
  - Нулевая конфигурация: инициализация выполняется прозрачно через вызов `init_db()` из стандартной библиотеки Python `sqlite3`.
  - Высокая производительность: сложные аналитические запросы с оконными функциями `ROW_NUMBER() OVER (PARTITION BY item_id ORDER BY timestamp DESC)` выполняются за миллисекунды благодаря индексу `(item_id, timestamp)`.
- **Отрицательные:**
  - Ограниченная горизонтальная масштабируемость (для персонального инструмента игрока не требуется).
  - Необходимость периодического запуска `prune_snapshots` для предотвращения разрастания дискового пространства.
